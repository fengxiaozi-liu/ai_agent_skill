# Speckit Doc

Speckit Doc 用于把代码语言、架构讨论、改造方案或 feature 产物翻译成文档语言，生成和维护 `docs/architecture.md`。

本技能使用 CodingDoc 表达模型：先按 `架构 / 单元 / 单元详情` 建立文档骨架，再按表达对象加载 `references/` 中的语法文件，并以 `assets/template.md` 作为文档起点。输出应形成标准设计文档形态：架构先给系统边界和分层关系，单元再展开内部协作和关键运行流程，单元详情最后沉淀实体、值对象、契约和实现规则。

## 何时使用

- 需要为当前仓库首次建立标准化架构文档时，使用 `init`。
- 已存在 `docs/architecture.md`，需要结合当前 feature 的 `spec.md`、`plan.md`、`tasks.md` 更新架构文档时，使用 `update`。
- 用户明确要求生成、维护、补全系统架构文档、核心流程图、实体说明或关键实现规则时。

## 职责边界

- `speckit-doc` 只负责生成和维护 `docs/architecture.md`。
- `speckit-doc` 只基于仓库事实、现有文档、以及 speckit 产物进行归纳，不捏造不存在的模块、流程、实体或依赖。
- 若信息来自代码与配置，按“已实现事实”表述。
- 若信息来自 `spec.md`、`plan.md`、`tasks.md` 但尚未完全落地，按“目标设计”或“规划中”表述。
- 文档结构必须遵循 `assets/template.md` 的 `架构 / 单元 / 单元详情` 骨架，不允许随意增删核心章节。
- 若仓库事实不足以支撑某节内容，明确标注“待补充”或“不适用”，不得虚构。

## 输入

### `init`

- 仓库根目录下的代码、配置、README、现有系统文档。
- 可按需读取项目适配技能或相关规范，抽取工程事实。

### `update`

- 已存在的 `docs/architecture.md`。
- 当前 feature 的 `specs/<feature>/spec.md`。
- 当前 feature 的 `specs/<feature>/plan.md`。
- 当前 feature 的 `specs/<feature>/tasks.md`。
- 与该 feature 相关的代码、配置和文档变更。

## 输出

- 标准模板：本技能目录下 `./assets/template.md`。
- 语法规范：本技能目录下 `./references/architecture-syntax.md`、`./references/flow-syntax.md`、`./references/entity-syntax.md`、`./references/state-syntax.md`。
- 目标文档：`docs/architecture.md`。

## 文档骨架

`docs/architecture.md` 使用三个一级部分：

```text
CodingDoc =
  架构
  + 单元
  + 单元详情
```

| 部分 | 职责 | 典型内容 |
| --- | --- | --- |
| 架构 | 描述整体结构和边界。 | 系统边界、架构图、单元职责、外部依赖、上下游关系。 |
| 单元 | 描述某个单元如何工作。 | 组件关系、调用链、流程、状态流转、能力装配、关键场景行为。 |
| 单元详情 | 描述可实现细节。 | 实体关系、实体字段、值对象、接口契约、存储语义、关键规则。 |

## 工作流

### 1. 模式判定

- 若用户要求首次建档、初始化架构文档、补齐仓库架构全貌，执行 `init`。
- 若用户要求根据某个 feature 的 speckit 产物更新架构文档，执行 `update`。

### 2. 事实抽取

优先从以下信息源抽取事实：

1. 代码目录结构。
2. README、已有架构文档、接口说明。
3. 关键配置文件。
4. `spec.md`、`plan.md`、`tasks.md`。
5. 与 feature 直接相关的实现文件。

抽取时至少识别：

- 系统边界与主要模块。
- 模块间调用关系或数据流。
- 核心业务流程。
- 核心业务实体。
- 外部依赖或基础设施。

### 3. 标准化归档

1. 读取本技能目录下 `./assets/template.md` 作为文档起点。
2. 根据表达对象按需读取 `./references/` 中的语法文件。
3. 按 `架构 / 单元 / 单元详情` 组织 `docs/architecture.md`。
4. 所有章节使用统一命名、统一术语、统一图示风格。
5. 最终文档只保留项目架构结果，不保留 speckit 过程痕迹。

### 4. `init` 规则

- 若 `docs/architecture.md` 不存在，则创建。
- 若已存在，但用户明确要求重新初始化，则基于当前仓库事实整体重建。
- 必须区分“仓库已实现事实”与“推断/待确认内容”。
- 使用 `assets/template.md` 作为骨架，将占位内容替换为当前项目事实。

### 5. `update` 规则

- 先读取已有 `docs/architecture.md`。
- 再读取 `spec.md`、`plan.md`、`tasks.md`，识别新增或变更的模块、流程、实体、依赖、边界。
- 仅更新受影响章节，保持未受影响内容稳定。
- 若 `tasks.md` 显示功能尚未完成，则在文档中以“规划中”或“待实现”标注，不写成既成事实。
- 更新后确保术语、图示、章节编号和实体命名保持一致。
- 更新结果直接并入对应章节，不追加变更流水或过程记录。

## 语法按需加载

按当前任务需要加载语法文件，保持渐进式披露。

| 使用场景 | 加载文件 | 适用章节 | 主要内容 |
| --- | --- | --- | --- |
| 描述系统边界、单元关系、外部依赖 | `references/architecture-syntax.md` | 架构 | 系统边界、单元关系、依赖方向、外部系统、数据/控制流。 |
| 描述实体、字段、存储关系 | `references/entity-syntax.md` | 单元详情 | 实体字段、E-R、主键、外键、索引、枚举、默认值。 |
| 描述流程、调用链、异常路径 | `references/flow-syntax.md` | 单元 | 流程、时序、入口、分支、输出、错误路径。 |
| 描述状态生命周期 | `references/state-syntax.md` | 单元 | 状态、状态迁移、触发条件、终态。 |

## 编写约束

- 使用正向描述：写当前设计需要表达、实现和保持的内容。无关内容默认不出现；影响实现边界或容易导致误实现的排除项，才写成明确规则。
- 章节名称使用 `架构`、`单元`、`单元详情`，图表类型只作为章节内的表达方式。
- 单元关系属于 `架构`；组件关系、流程和状态属于 `单元`；实体关系、字段和存储语义属于 `单元详情`。
- 使用 SysML 作为语义参考，用 Mermaid 作为图表呈现方式。
- 优先使用表格和 Mermaid，少写大段散文。
- 未确认内容放入假设或待确认问题；已经确认的选择写入对应章节。
- 用户明确要求计划时，再包含实施步骤。
- 每个流程都应包含入口、分支和终止输出。
- 每张运行流程图下方都应紧跟流程说明，优先使用步骤表。
- 每个实体都应包含字段、含义、关系和关键存储语义。
- 不要把实现事实拆得过碎：避免把每个包、文件、函数都变成独立章节；优先聚合为后续 AI 实现时需要理解的单元、组件、场景和契约。
- 对外部系统、基础设施、值对象、DTO、工具协议、事件、配置等非持久化对象，应根据实现影响放入 `单元详情` 的 `值对象与契约`，不要强行塞进 E-R 图。
- `关键实现规则` 应使用三列表格：`规则 / 所属单元 / 实现语义`；规则必须能指导后续实现或评审。
- 标题应使用稳定层级编号：`1.1 系统边界`、`1.2 架构图`、`2.1 [单元] 组件关系`、`3.4 关键实现规则`。

## 图表表达规则

- `架构` 章节默认只生成一张 `架构图`：用分层 `subgraph` 表达层级结构，并在同一张图中保留关键单元关系；不要再额外生成独立的 `单元关系图`。
- 架构图按从上到下排序，推荐层级为：宿主应用层、服务层、领域层、能力接入层、基础设施层、外部系统层。
- 架构图应同时使用 `classDef/class` 和必要的 `style subgraph` 给不同层级设置区分颜色；颜色表达层级，不表达运行状态。
- 组件关系图属于 `单元` 章节，用于表达单元内部协作结构；优先用 `subgraph` 按职责分组，不画运行分支。
- 运行流程图属于 `单元` 章节，用于表达入口、分支、回环、终止输出和异常路径；每张流程图都必须有明确 `开始` 节点和一个或多个明确结束节点。
- 运行流程图优先按阶段划分 `subgraph`，例如请求接入、上下文准备、执行循环、终止输出；每个阶段应使用 `classDef/class` 或 `style` 表达分组。
- 运行流程图下方必须有图下说明：简单流程使用 `步骤 / 执行者 / 动作 / 输出` 表，复杂流程可增加 `节点 / 完整语义 / 实现影响` 或异常路径表；图中短名和图下说明必须互相印证。
- 时序图适合表达跨组件调用顺序；当时序关系已经清晰时，不需要为了统一风格改成 flowchart。
- 实体关系图属于 `单元详情` 章节，优先使用 `erDiagram`；字段和存储语义由后续字段表承接，不要把所有字段规则塞进图中。
- Mermaid 节点文本统一使用 `["..."]` 或 `{"..."}` 包裹，避免括号、逗号、斜杠、问号等字符导致渲染器解析失败。
- 图表只保留主调用链和关键支撑关系，避免把所有包级、函数级依赖都画成连线；细粒度依赖用表格、步骤表或后续流程图承接。

## Mermaid 可读性规则

- 优先保证“人眼可读”，不要为了把完整语义放进一张图而牺牲字号；完整语义用步骤表、职责表、契约表承接。
- 单张 flowchart 建议控制在 5-8 个主要节点；超过 10 个节点、超过 2 个 `subgraph`、出现 2 条以上跨阶段长回线，必须拆成多张连续小图。
- 复杂流程按阶段拆分为 `2.x.1`、`2.x.2`、`2.x.3` 等连续小节，例如 `请求接入`、`上下文准备`、`模型与工具循环`、`终止输出`；用“进入下一阶段”“来自上一阶段”这样的短终端节点保持流程连续性。
- 单张图不要同时表达装配、执行、权限、异常、外部系统等多个维度；每张图只表达一个关注点。需要多个关注点时拆成“装配图 / 执行图 / 权限图 / 异常图”。
- 节点文案必须短：优先使用 2-6 个汉字或一个短英文标识。长包名、函数名、英文协议名、参数细节放到图下方表格，不放进节点。
- 如果节点文案超过 12 个中文字符或 3 个英文单词，应缩写节点文本，并在后续表格解释完整名称和语义。
- 会撑宽图的枚举、适配器列表、工具列表不要平铺到 flowchart 中；改用表格列出，或用一个聚合节点表示。
- 跨组件调用顺序优先使用 `sequenceDiagram`，不要把 provider/client/factory/adapter/外部 API 全部平铺成 flowchart。
- 需要改善渲染字号时，可在 Mermaid 块开头加入初始化配置，例如 `%%{init: {"themeVariables": {"fontSize": "16px"}}}%%`；但字号配置不能替代拆图，单图过宽时必须拆。
- 如果用户反馈“图看不清”“字体太小”“横向太宽”“Mermaid 预览糊”，优先执行拆图、缩短节点文案、用表格承接细节，而不是只把 `LR` 改成 `TD`。

## 标准形态检查

输出前按以下规则检查：

| 检查项 | 标准 |
| --- | --- |
| 架构粒度 | 一张分层架构图 + 一张单元职责表；架构图不展开单元内部运行分支。 |
| 单元粒度 | 每个重点单元至少包含组件关系、流程或时序之一；复杂系统可拆 3-6 个单元小节。 |
| 流程完整性 | 流程图有开始、入口、条件分支、关键回环、成功/取消/错误等终止路径；每张运行流程图下方都有步骤表或说明表补足精确动作、输出和异常语义。 |
| Mermaid 可读性 | 单张图不应因横向过宽被预览器压缩到文字不可读；复杂流程必须拆成连续小图，节点短名 + 表格补语义。 |
| 详情完整性 | 持久化实体用 E-R 和字段表；非持久化契约、事件、配置、工具参数用值对象与契约表。 |
| 规则可执行性 | 关键规则能直接约束编码、测试或评审；只写当前设计确实需要保持的语义。 |
| 抽象程度 | 规则和模板不绑定具体项目名、包名或业务名；具体内容只出现在用户请求的目标文档中。 |

## 质量标准

一份合格的 `docs/architecture.md` 应让后续 AI 编程代理回答这些问题：

| 问题 | 文档中应提供的答案 |
| --- | --- |
| 这个设计处在系统哪里？ | `架构` 章节。 |
| 系统有哪些单元以及它们如何依赖？ | `架构` 章节的单元关系。 |
| 某个单元内部如何协作？ | `单元` 章节的组件关系、流程或状态。 |
| 需要哪些数据结构和关系？ | `单元详情` 章节的实体、字段和 E-R。 |
| 实现时需要保持哪些关键语义？ | `单元详情` 章节的字段、关系和存储语义。 |

## 执行提示

- 如果仓库内已存在其他架构文档，可将其作为事实来源之一，但不得把某个具体项目的章节设计或业务术语固化进通用技能。
- 如果项目存在明显的工程适配技能，应结合适配技能理解项目分层、模块职责与交付边界。
- 若实体较多，仅保留对系统理解最关键的实体，不做 ER 全量穷举。
